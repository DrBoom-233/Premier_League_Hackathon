# PitchGuard AI 合成动画制作规划

版本：v0.3 | 日期：2026-10-22 | 状态：动画生成实现已落地，人工验收与 VLM 联调待完成

本文件用于团队内部执行，采用中文说明；提交给评委的场景介绍、界面和演示材料使用英文。当前已确定采用 GPT 编写 Blender Python 脚本、Blender 程序化生成动画、预训练 VLM 分析画面的路线；人物和动作由脚本创建，不依赖外部角色或动作素材库。制作实现、实测信息与运行命令见 [动画交付说明](../data/animation/README.md) 和 [制作记录](../data/animation/generation_notes.md)。下文保留制作方案与验收要求，不代表所有验收均已通过。用户本轮确认先完成动画素材，真实 VLM 联调留待后续。

当前实现入口：`scripts/animation/build_scene.py`；通过 `scripts/animation/render.ps1` 重建 S001–S003 及独立参考 R001。完整素材与 Blender 工程位于本机 `data/animation/runtime/`、`data/animation/scenes/`，大文件不进入 Git。运行时清单与制作参数、评估文件分开保存；人工标注仍为空，不以制作意图冒充标注。

## 1. 目标与交付范围

制作一组可重复播放、具有时间标记的足球球员动作短片，供动作分析 Agent 直接通过 VLM 观察，并与历史信息和合成比赛事件关联。

首版交付：

- 一个由几何体组成、有明确躯干和四肢的虚构人形球员、一个简单球场区域、一个固定镜头模板。
- 三个约 10 秒的核心片段：稳定跑动、跑动后减速停步、局部遮挡。
- 每段对应的完整渲染帧、少量 VLM 输入帧、时间清单和仅供评估的人工标注。
- GPT 编写并经检查的生成脚本、场景配置、可编辑 Blender 工程，以及实际 VLM 测试结果。

先用一个片段打通制作和推理流程，再制作其他场景。首版不依赖模型训练、姿态提取、全场多人追踪、复杂球场建模或精确生物力学模拟。

本批动画验证的是“可见动作观察、证据引用和 Agent 协作”。减速、停步或左右动作差异不等于伤病；预设变化也不是医学上的伤病真值。系统输出关注状态和证据，伤病概率保持未验证状态。

## 2. 推荐工具与选择理由

| 工具 | 用途 | 首版使用方式 |
|---|---|---|
| GPT / 编码助手 | 编写和迭代 Blender Python 脚本 | 根据场景要求生成一次可复用脚本，结合预览与报错修正 |
| Blender Python API（bpy） | 创建人物、编排动作、布置场景与渲染 | 使用几何体、父子关节层级、位置/旋转关键帧，按配置生成片段 |
| Blender 图片序列与视频输出 | 生成视频及图片 | 先输出 PNG 帧，再合成 MP4；从同一批帧中选择 VLM 输入 |
| 现有后端与 Foundry VLM | 执行真实观察 | 按现有架构发送有序图片和时间戳，保存结果与耗时 |

整体流程为：场景要求 → GPT 编写脚本 → Blender 执行并预览 → 人工检查/反馈 → 修改脚本或参数 → 批量渲染 → VLM 分析。GPT 负责产出代码和修改建议，Blender 负责实际计算与出图；不是每一帧都调用 GPT，也不需要 GPT 自动生成视频像素。

Blender 支持从 Python 操作场景和插入关键帧，也支持命令行执行脚本。[Python 快速入门](https://docs.blender.org/api/main/info_quickstart.html)

第一阶段确认本地 Blender 版本、Python API 和渲染/编码是否可用。首版采用实体感的简化人形角色，不追求写实人物；其动作是否可读、VLM 是否能理解，必须通过短预览验证。复杂自然步态、精确接触与医学真实性不作为默认能力。

## 3. 场景清单

| ID | 优先级 | 时间安排 | 检查目标 |
|---|---|---|---|
| S001 | 必做 | 0–10 秒稳定跑动 | 能描述活动；避免凭空声称球员受伤 |
| S002 | 必做 | 0–5 秒跑动；5–8 秒减速至行走；8–10 秒停步 | 能定位可见变化，并与参考跑动区分 |
| S003 | 必做 | 复用 S002 动作；约 4–6 秒遮挡腿部，其余时间可见 | 能指出视野不足，复查时只引用重新可见的证据 |
| S004 | 可选 | 清楚可见的左右动作差异 | 通过脚本分别调整左右腿摆幅/节奏；先人工确认可读性，不作为医学伤病模拟 |
| S005 | 可选 | 保持稳定动作，改变镜头角度 | 检查是否把镜头变化误当作球员异常 |

S002 的变化用于模拟一段待解释的比赛活动，不能标成“未来必然受伤”。如增加 S004，应由人检查动作确实可见，且没有骨骼变形、穿模或足部滑动等明显制作错误。

S003 是同场景的遮挡对照，不与 S002 分到不同的独立评估集合。补充更密集帧只能帮助检查可见区间；遮挡期间不存在的视觉信息无法被恢复，也不要求复查一定成功。

## 4. 制作流程

### 阶段 A：GPT 生成脚本与最小可行验证

1. 确认 Blender 可以运行，记录版本；由 GPT 根据该版本生成 `build_scene.py`，在 Blender 的 Python 环境执行。
2. 脚本创建头部、躯干、骨盆、上下臂、大小腿和足部，使用球体/圆柱体等基础几何体及简单材质。首版用父子变换层级和关节枢轴，不必先完成蒙皮与写实建模。
3. 用关节旋转和关键帧编排一段 2–3 秒的跑动近似：双腿交替、手臂配合、膝部弯曲和有限躯干起伏。动作参数要有可读的名称和范围，便于人工调整。
4. 脚本同时创建地面、光照、侧面或斜侧面固定镜头，并保存工程和少量预览帧。
5. 人工检查连贯性、关节连接、脚部接地与构图；把报错和预览问题反馈给 GPT 修改。通过后调用一次 VLM，确认它能识别大致活动。

通过条件：脚本可运行，人工能辨认活动，VLM 输出可关联到输入帧。若画面不可读，先改人物比例、关节动作、镜头或光照，再制作完整片段。脚本成功执行不等于动作质量已经通过验收。

给 GPT 的首轮制作要求可以写为：

> 使用指定版本的 Blender Python API 创建一个有实体躯干和四肢的简化人形角色、平面球场、固定斜侧面相机及光照。先制作一段 3 秒的可读跑动预览，使用父子关节层级和位置/旋转关键帧。脚本只向指定输出目录保存工程、图片和日志，支持配置帧率、时长、动作参数及场景 ID。不要下载模型或动作，不要将评估标签写进画面。先给出可运行脚本，运行后根据报错和预览修正。

### 阶段 B：制作统一模板

1. 固定角色、服装、场景、光照、相机、帧率和分辨率。
2. 脚本统一控制关节动作和根节点路径：调节步频/摆幅时同步调整空间位移；脚部处于支撑阶段时检查是否明显滑动。
3. 调整路径与构图，使目标人物在整个片段内保持足够大、全身可见。
4. 保存生成脚本和基础工程，各场景通过配置复用同一人物与动作函数，而不是每段让 GPT 重新编写一整套代码。

程序平移一个模型不等于改变其跑步动作。制作 S002 时，身体动作与空间位移都需要合理过渡，避免“脚仍然冲刺、身体却停止”等错误。

### 阶段 C：参数化动作与对照场景

1. 使用相同人物、关节层级和动作函数，固定参数生成 S001 的稳定跑动。
2. 用按时间变化的步频、摆幅和根节点速度生成 S002，在减速阶段平滑过渡到行走和站立；保存位置/旋转关键帧。
3. 检查转换时动作相位是否连续，清理瞬移、关节跳变、重复人物和明显穿模。简单周期公式只用于动作原型，不视为真实步态模型。
4. 复制 S002，增加简单遮挡物或经过画面的普通物体，制作 S003。
5. 对照版本尽量只改变一个因素；服装、镜头或亮度不应暗示当前片段的标签。

核心动作直接由脚本生成关键帧；后续确有手工编辑需求时才使用 Action/NLA 等工具。Blender 的 `keyframe_insert` 支持通过 Python 插入动画关键帧。[官方 API](https://docs.blender.org/api/current/bpy.types.bpy_struct.html)

### 阶段 D：渲染与输入帧选择

建议起始参数如下，第一段预览后可调整，并记录实际值：

| 参数 | 起始配置 |
|---|---|
| 片段长度 | 约 10 秒 |
| 分辨率 | 1280 × 720 |
| 视频帧率 | 24 fps |
| 场景 | 简单草地或平面，无观众和复杂建筑 |
| 相机 | 固定侧面或斜侧面，腿部可见 |
| 渲染方式 | 从低成本预览开始，优先可读性；使用团队已验证的快速设置 |
| 完整帧输出 | PNG 图片序列 |
| 播放视频 | MP4/H.264，以本地编码支持情况为准 |
| 初次 VLM 输入 | 每段约 8–12 张有序帧，参考帧另计 |

先渲染少量代表帧，测量单帧耗时，再估算总耗时。10 秒、24 fps 共 240 帧；如果单帧耗时为 r 秒，单段渲染约需 240r 秒，编码、加载和其他开销另计。这是估算公式，不是性能承诺。

保留完整帧以便一次有界复查。初次输入优先按时间均匀抽样，不利用隐藏标注专门挑中“异常”瞬间；补充帧由 Agent 请求的时间范围决定。参考帧使用同一人物、同类活动的独立参考片段，并计入请求的图片数量和费用。

Blender 的图片序列流程允许保留逐帧输出，之后再合成视频。[官方渲染流程](https://docs.blender.org/manual/id/5.1/render/output/animation.html)

### 阶段 E：人工标注与联调

1. 人工检查完整视频，记录实际可见动作和大致时间范围。
2. 检查相邻帧顺序、视频时长、帧号与时间戳是否一致。
3. 将动作时间映射到统一的合成比赛时钟。
4. 运行真实 VLM 调用，保存输入帧清单、模型/提示词版本、输出、延迟和用量。
5. 将观察交给证据调查 Agent，演示一次有明确理由的复查或拒绝判断。

原始制作设定必须经过人工看视频确认后才能成为评估标注。不要将制作参数、未来伤病或预期答案发送给模型。

## 5. 文件组织与交付物

以下为原规划目录；现有实现与新增检查工具以动画交付说明为准：

```text
scripts/animation/
  build_scene.py              已实现的可复用 Blender 生成脚本
data/animation/
  README.md                   制作步骤、Blender 版本和运行方式
  generation_notes.md         GPT 生成/修改记录、脚本版本和预览问题
  configs/                    每个场景的制作参数，仅供生成与评估
  scenes/                     可编辑 Blender 工程
  runtime/
    S001/
      video.mp4               无答案提示的合成画面
      frames/                 全部渲染帧，供抽样或复查
      input_manifest.json     帧清单、时间、目标人物和参考片段
  evaluation/
    annotations.json          人工确认的动作与可见性标注
    results/                  模型输出和人工核对结果
```

文件夹、文件名和提示词使用中性编号；不要出现 `injured`、`limping` 或 `high_risk` 等当前片段答案。评价文件仅供离线检查，不由动作 Agent 的工具读取。

脚本与小型配置保存在仓库；较大的工程和图片序列可以保存在团队约定的共享存储，仓库中保留说明、清单和必要小样。首版人物、材质与动作由脚本创建；后续若引入任何第三方资产，再记录对应来源与使用条件。

生成脚本的接口如下；经过实测的执行命令见动画交付说明：

```text
输入：场景 ID、时长、帧率、随机种子、镜头、动作参数、输出目录
执行：Blender 内置 Python 运行 build_scene.py
输出：可编辑 .blend、渲染帧、MP4、输入清单、渲染日志
```

同一脚本版本和配置应能重建相同场景。制作参数可能暴露预期变化，必须与运行时 `input_manifest.json` 分开保存，VLM 工具只读取运行时允许的数据。

## 6. 与 Agent 的数据接口

运行时清单示例，仅说明结构，文件路径和 ID 在制作后替换为实际值：

```json
{
  "schema_version": "1",
  "scenario_id": "S001",
  "player_id": "P001",
  "data_mode": "synthetic",
  "duration_ms": 10000,
  "fps": 24,
  "render_frame_start": 1,
  "match_start_ms": 4080000,
  "video_path": "video.mp4",
  "reference_clip_id": "R001",
  "frames": [
    {
      "frame_id": "S001_F0001",
      "path": "frames/frame_0001.png",
      "clip_time_ms": 0,
      "match_time_ms": 4080000
    },
    {
      "frame_id": "S001_F0025",
      "path": "frames/frame_0025.png",
      "clip_time_ms": 1000,
      "match_time_ms": 4081000
    }
  ]
}
```

示例清单只列出两项以说明格式，实际文件应列出需要服务端访问的完整帧。图片按照 `clip_time_ms` 排序发送。时间映射规则：

```text
clip_time_ms = (frame_number - render_frame_start) × 1000 / fps
match_time_ms = match_start_ms + clip_time_ms
```

场景 ID 可以用于找到同一球员的历史快照和公开的比赛上下文；隐藏动作标签和未来伤病结局不进入接口。必要的目标人物高亮可保持一致，但不能按风险等级变色。演示用的“AI 结果叠加层”应与输入原图分离，避免模型读取自己的答案。

VLM 任务示例：

> Compare the target player's visible movement in the ordered current frames with the reference frames. Describe clear changes in activity or movement, cite supporting frame IDs, and distinguish observations from hypotheses. If visibility is insufficient, state what is obscured and which interval would benefit from more frames. Do not infer a diagnosis or provide an injury probability.

建议输出字段：`observations`、`evidence_frame_ids`、`view_status`、`limitations`、`review_status`，以及可选的 `requested_recheck`。含义与 [Agent 架构](ARCHITECTURE.md) 一致。看不出变化也是允许的结果，不能要求模型每次报异常。

## 7. 验收标准

### 制作与数据验收

- [x] 三个核心场景已生成 H.264 视频，时长、帧率和清单一致；自动检查记录见 `data/animation/evaluation/results/verification.json`。
- [x] 同一模板的正常对照与变化场景在人物、服装、光照、镜头上保持一致。
- [ ] 人工可辨认预期的可见变化，或明确辨认遮挡位置。
- [ ] 没有明显瞬移、足部滑动、骨骼破损或拼接伪影主导观察结果。
- [x] 复查帧可从原始完整帧中获取，时间映射正确。
- [ ] 保留生成脚本、配置、Blender 版本与工程，团队另一成员可以重复生成一个片段。

### 模型与系统验收

- [ ] VLM 使用实际图像输入，帧引用能够定位到画面。
- [ ] 分别记录稳定片段、变化片段、视野不足片段的成功与失败，不用预设答案替代推理。
- [ ] 未识别、误报和复查失败都保留在结果表中；根据失败决定缩小场景或改善画面。
- [ ] 稳定片段用于检查误报；变化片段用于检查观察与时间定位；遮挡片段用于检查拒绝判断。
- [ ] 更密集抽帧产生的复查只能支持可见区间，不能编造被遮挡期间的动作。
- [ ] 未把关注等级或 VLM 自报置信度当作伤病概率。
- [ ] 一次完整协作能从画面、历史摘要到解释走通，并记录真实耗时和用量。

三条核心片段是联调素材，不足以证明泛化能力。通过联调后，若时间允许，将不同动作实例、相机或遮挡条件扩展到约 10–15 个场景；先按基础动作实例划分调试集和留出检查集，再制作其衍生版本。保持成对/重复片段在同一集合，留出集结果不用于反复改提示词。

## 8. 执行节奏与分工

以一个工作日左右作为首轮安排，具体取决于脚本调试、动作质量和实测渲染速度；不承诺当日一定完成。GPT 编写代码可以减少手工建模操作，但不会省去预览与质量检查。

| 工作包 | 建议时间盒 | 负责人职责 | 通过后产物 |
|---|---|---|---|
| A：最小验证 | 1–2 小时 | 制作负责人让 GPT 编写并调试脚本，Agent 负责人确认图像接口 | 一个可运行脚本、可读预览和一次真实 VLM 结果 |
| B：模板与首片 | 1–2 小时 | 制作负责人固定镜头、动作和输出参数 | S001、可编辑模板、实际渲染耗时 |
| C：变化与遮挡 | 2–3 小时 | 制作负责人调整参数与动作转换；评估负责人检查伪影 | S002、S003、人工标注 |
| D：联调与交付 | 1–2 小时 | Agent 负责人接清单，评估负责人核对结果 | 可复查证据、结果表、团队使用说明 |

角色可以由同一人兼任，当前不指定成员。每个时间盒结束时只决定下一步是否值得继续：最小验证失败时先修画面或接口，避免同时堆积多个未验证场景。

## 9. 常见问题与降级方案

| 问题 | 处理方式 |
|---|---|
| GPT 生成脚本报错或 API 不兼容 | 固定 Blender 版本，保留报错和最小预览配置，逐个修正后再批量运行 |
| 简化人物无法被 VLM 识别 | 改善实体比例、关节连接、材质和镜头，人工先检查可读性 |
| 程序化步态不自然 | 缩小动作范围，先保证基本跑动与停步连贯；复杂左右差异留到核心场景通过后 |
| 动作切换跳变或脚滑 | 修动作衔接及位移，必要时用单一连续动作制作变化；不能把制作伪影标成球员异常 |
| 渲染耗时太长 | 降低画面复杂度、分辨率或片段长度，复用已完成帧；优先保证人物可读 |
| VLM 看不清人物 | 增大目标、改善光照与构图，先验证受控视角 |
| VLM 没看出变化 | 先检查人是否看得出，再调整素材/采样；保留失败，不向模型泄露标签 |
| 抽帧漏掉短暂变化 | 对请求区间补充帧一次；仍无证据则保持不确定 |
| 只来得及制作稳定跑动与遮挡 | 展示真实观察和正确拒绝判断；说明尚未完成变化场景，不宣称已实现伤病预测 |

## 10. 与比赛和后续开发的关系

这组素材支撑合成事件输入、动作解释、同步叠加、个性化呈现和 Agent 复查证据。比赛规则要求合成足球数据，并要求对所使用素材拥有必要权限；项目展示应明确说明是合成回放和采样帧分析。[官方规则 §4.1、§4.7](https://github.com/microsoft/insidethegamehackathon/blob/main/OFFICIAL%20RULES.md)

首版完成后，按实际失败再决定是否增加动作类型、多个球员、镜头变化、姿态特征或训练模型。现阶段的优先级是可读、可控、可复现和可联调。
